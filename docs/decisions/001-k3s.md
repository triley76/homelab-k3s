# ADR-001: Use K3s as the Kubernetes Distribution

## Status

Accepted

## Context

The platform requires a Kubernetes distribution suitable for a multi-node infrastructure lab running as virtual machines on VMware Workstation.

The environment is intended to support hands-on engineering work around:

- Kubernetes architecture

- Infrastructure automation

- High availability

- Cluster lifecycle management

- GitOps

- Networking

- Storage

- Observability

- Failure and recovery testing

The cluster needs to behave as a real multi-node Kubernetes platform while remaining practical to operate within the compute and memory available to a workstation-based lab.

The infrastructure also needs to be reproducible through automation rather than depending on a manually constructed cluster.

## Decision

Use **K3s** as the Kubernetes distribution for the platform.

The current V2 implementation pins K3s to:

```text

v1.36.4+k3s1

```

The architecture uses three K3s server nodes with embedded etcd.

K3s installation and cluster formation are automated through Ansible.

## Rationale

### Kubernetes Compatibility

K3s provides a Kubernetes environment that supports the APIs and operational patterns required by the platform.

This allows the lab to exercise technologies and practices such as:

- Kubernetes workloads

- Services

- Ingress

- Persistent storage

- GitOps

- High-availability control-plane behavior

- Cluster networking

- Observability

without requiring a larger infrastructure footprint solely to host the Kubernetes control plane.

### Resource Efficiency

The platform runs on workstation-hosted virtual machines.

A comparatively compact Kubernetes distribution allows more of the available compute and memory to remain available for:

- Multiple control-plane nodes

- Platform services

- Application workloads

- Failure testing

- Additional lab systems

Resource efficiency is therefore an architectural consideration rather than merely a convenience.

### Automation

K3s fits the project's automation model.

The deployment can be expressed through Ansible and integrated into the existing sequence:

```text

Packer

  |

  v

Ubuntu VM

  |

  v

PowerShell VM automation

  |

  v

Ansible

  |

  v

K3s

```

This keeps Kubernetes installation out of the base VM image and makes cluster construction part of the configuration-management layer.

### High-Availability Architecture

K3s supports a multi-server configuration using embedded etcd.

This allows the lab to implement a three-node control plane without requiring a separately managed external datastore.

Combined with kube-vip, the architecture provides:

```text

           Kubernetes API VIP

                    |

        +-----------+-----------+

        |           |           |

        v           v           v

      k3s01       k3s02       k3s03

        \\           |           /

         +----------+----------+

                    |

              embedded etcd

```

This architecture has been exercised through a controlled single-server failure and recovery test.

### Version Control

The K3s version is explicitly pinned in the cluster configuration.

This prevents automated rebuilds from silently selecting a newer release and makes the deployed software version visible in source control.

## Alternatives Considered

### kubeadm

`kubeadm` would provide a more component-oriented Kubernetes installation and expose more of the upstream cluster-construction process.

That can be valuable for some learning and production scenarios, but it would also introduce additional installation and lifecycle complexity into this particular workstation-based platform.

The primary objective of this project is broader platform engineering rather than manually assembling every Kubernetes control-plane component.

### Full Kubernetes Distributions

Larger Kubernetes platforms could provide additional integrated capabilities.

For this lab, however, they would also increase infrastructure requirements and potentially hide some of the individual platform layers the project is intended to build and examine independently.

### Single-Node Kubernetes

A single-node implementation would reduce resource consumption further.

It was rejected for the V2 architecture because it would not provide the multi-node control-plane, quorum, API failover, and node-recovery behaviors the project is intended to explore.

## Consequences

### Positive

- Lower infrastructure overhead than a heavier Kubernetes deployment

- Straightforward automation through Ansible

- Support for a three-server HA architecture

- Embedded etcd support

- Kubernetes-compatible platform for GitOps and workload testing

- More workstation resources remain available for additional platform services

- Version can be pinned explicitly for reproducible builds

### Tradeoffs

- K3s packages and manages parts of the Kubernetes installation differently from a cluster assembled directly with kubeadm.

- Some operational details are specific to K3s.

- Experience with this platform should not be represented as evidence that every Kubernetes distribution behaves identically.

- A lightweight distribution does not remove the need to understand the Kubernetes architecture underneath it.

## Validation

The V2 implementation has successfully:

- Installed the pinned K3s release

- Initialized the first server

- Joined two additional server nodes

- Formed a three-node embedded-etcd control plane

- Served the Kubernetes API through kube-vip

- Continued serving the API after a controlled failure of the current VIP-owning server

- Reintegrated the failed server after it was restarted

- Supported Flux GitOps reconciliation

The validation scope is documented in:

```text

docs/validation.md

```

## Result

K3s provides the balance this platform currently requires: a real multi-node Kubernetes environment with high-availability capabilities, while remaining practical for automated deployment and repeated experimentation in a workstation-based lab.

This decision can be revisited if future platform requirements require capabilities or operational characteristics better served by another Kubernetes distribution.
